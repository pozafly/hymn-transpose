# 찬송가 조옮김 서비스 핸드오프

2026-09-24 업데이트. Next.js + TypeScript / Node.js + pnpm 기반 가족용 개인 악보 보관함.
배포 대상은 자택 Proxmox 위 Ubuntu + Docker Compose + Cloudflare Tunnel이다.
장모님 한 분이 비밀번호로 로그인해 사용한다. 앱 이름은 **유나와 함께 찬송을**이다.

## 구현 현황

- 기본 찬송가와 개인 업로드를 번호·제목으로 검색한다. 중복 번호도 별도 ID로 보관한다.
- 보관함은 출처와 관계없이 찬송가 번호 오름차순이다. 같은 번호는 기본 악보, 개인 악보 등록일, ID 순서로 고정하고 번호 없는 악보는 마지막에 둔다.
- 사진 업로드 → Audiveris(Java) 분석 → 원본과 미리보기 확인 → 여러 조 생성 → PDF·PNG 저장.
- 제목·번호 수정, 장·단조 보정, 실패 재시도, 조별 결과 보관.
- HttpOnly 쿠키 + SQLite 서버 세션. JWT가 아니다. 모든 화면·API·파일에 인증 적용.
- 원본·상태·작업 큐는 `library`, 결과물은 `scores` Docker 볼륨에 영속 저장한다.
- worker 재시작 시 실행 중이던 작업을 대기열로 복구한다. worker는 하나만 실행한다.
- `lib/cache.ts`가 상세 조회·API·파일 요청의 결과 버전과 파일 존재를 검사한다. 오래된 결과나 누락 파일은 필요한 조만 다시 생성한다.
- 작업 큐의 `generation` 열은 자동 마이그레이션한다. 이전 작업 결과는 현재 세대와 소스 해시를 확인한 뒤에만 반영한다.
- 엔진·폰트 변경 시 `.env`의 `SCORE_RENDER_VERSION`을 올리고 앱·worker를 함께 재시작한다. 자동 구버전 파일 삭제는 하지 않는다.
- Node.js에서 MusicXML을 검증하고 허용 문법의 LilyPond 소스만 생성한다. Python은 실행 경로에 없다.

전체 645개 원본의 등록 변환을 시도한 작업은 이미 완료되었다.
성공·기존 등록 포함 641개, 실패 4개(112·133·244·451장)다.
112·451장은 이조 악기 요소 미지원, 133·244장은 원본과 변환 후 음표 수 불일치로 등록을 거절했다.
로컬 PDF/PNG 추가 생성 범위는 사용자 요청대로 1~80장, 각 기본 조 하나다.
이후 사용자가 **원본 검사·수정만 645장 전체로 확대**했다. 81~645장 추가 검사는 완료했으며 아래 기록을 따른다.
전체 곡·전체 조를 미리 렌더하지 않는다. 이후 서버에서 이어 작업한다.
실제 자료는 Git에 없으며 별도 볼륨 이전 또는 가져오기가 필요하다.

1~80장 각각 기본 조의 PDF와 모든 PNG 페이지 생성·시그니처 검사는 **80/80 통과**했다.
보고서는 `data/reports/verification-80.json`과 Docker library 볼륨에 있으며 Git에서 제외한다.
작업 중 앱·worker를 재생성해 기존 세션·PDF 유지와 중단된 29장 작업의 자동 재실행도 확인했다.
최종 단위 테스트 11개, 데스크톱·모바일 E2E 12개, 타입 검사와 Docker 프로덕션 빌드가 통과했다.
E2E는 업로드·실제 OMR·장단조 변경·F/G 생성·번호 중복 검색·재접속·인증을 포함한다.

캐시 무효화·앱 이름 변경 후 단위 테스트 12개와 데스크톱·모바일 E2E 12개가 통과했다.
별도 실제 복구 시험에서는 1장 PNG를 임시 이동한 뒤 파일 요청의 202 응답,
worker의 PDF·PNG 재생성, 상세 조회와 다운로드 복구를 확인했다.
기존 결과 버전을 그대로 재사용했으며 80곡 전체 재생성은 하지 않았다.

사용자의 악보 신뢰성 검증 요청으로 1~80장 내용 대조를 추가했다.
67장 별도 템플릿을 제외한 79곡에서 원본→MusicXML→내부 데이터의 음표·가사·조표·박자가 일치했다.
최종 엔진 대조 중 단일 음표 붙임줄 출력 순서 오류를 찾아 수정했다(9곡 92개 음표의 출력 패턴).
수정 후 LilyPond 2.24.4의 성부별 MIDI와 원본의 음높이·시작 시점·길이가 79곡 모두 일치했다.
공식 홈페이지와 80곡 가사를 비교해 265개 절 중 262개가 일치했다.
당시 차이가 난 22·42·63장은 후속 전곡 원본 검사에서 GOODTV·인쇄 악보 이미지로 원본 표기를 확인해 유지했다.
이 대조는 유닛·E2E 실행 없이 진행했다. 인쇄본 전곡 대조나 서버 배포는 완료한 것이 아니다.
자세한 범위와 결과는 [악보 내용 대조](score-quality-audit.md)를 참고한다.

후속 요청에 따라 원본 81~645장 565곡을 추가 검사했다. 수정본을 포함한 음표 140,034개와
가사 위치 116,107개, 조표·박자가 MuseScore 3.6.2의 검수용 MusicXML과 모두 일치했다.
112·451장의 피아노 이조 설정, 133·244장의 성부 내 시간 중첩, 244장의 같은 화음 내 중복 음표,
220·519장의 가사 오타를 수정했다. 수정한 6곡은 MuseScore 3.2.3과 3.6.2 양쪽에서 음표 이벤트 대조를 통과했다.
원본 645개 중 639개는 바이트 단위로 그대로다. 1~80장 전곡 검사를 다시 돌리지는 않았다.
서버 전송용 원본은 `data/source-review/release/hymn-originals-reviewed-20260924.zip`에 묶었다.
이번에는 앱·운영 DB·캐시·서버를 변경하지 않았다. 전곡 PDF/PNG 생성과 유닛·E2E도 실행하지 않았다.
자세한 수정 근거, 검사의 한계, 서버 재등록 주의점은 [645장 원본 검사 기록](source-audit-645.md)을 참고한다.

서버 가져오기에서 `{"files":645,"success":0,"failed":0}`으로 끝나는 문제를 후속 수정했다.
Linux `unzip`이 검수본 ZIP의 한글 파일명을 깨뜨려 모든 파일이 번호 인식에서 제외되는 현상을 재현했다.
`lib/hymn-sources.ts`가 비암호화 ZIP을 Node.js로 직접 풀고 기존 암호화 ZIP은 `unzip`으로 읽는다.
등록 전에 파일명·번호 중복·등록 대상 수를 확인하고, 대상 0곡이나 곡별 변환 실패는 오류로 알린다.
Linux에서 검수본과 기존 암호화 원본 각각 645곡의 번호·제목·SHA-256 일치를 확인했다.
별도 임시 컨테이너에서 1장을 실제로 가져와 원본·MusicXML·DB 저장을 확인했고 타입 검사도 통과했다.
유닛·E2E, 전곡 변환, PDF/PNG 생성, 운영 볼륨 변경은 실행하지 않았다.
서버에서는 최신 코드를 받은 뒤 `Dockerfile.import` 이미지를 다시 빌드하고 가져오기를 재실행한다.
원본 ZIP은 그대로 사용하며, 이미 등록된 ID를 건너뛰는 동작도 유지한다.

## 유지할 규칙

기존 67장 `score/hymn67.ly.tmpl`의 `\key ges \major`와 레이아웃은 변경하지 않는다.
음표는 직접 조옮김하지 않고 LilyPond의 `\transpose`에 맡긴다.
기존 코드 심볼은 `chord_labels()`로 이명동음 철자를 지킨다(G♭ IV=C♭, F♯ IV=B).
사용자 `.ly`를 실행하지 않는다. 조는 화이트리스트로 검증한다.
LilyPond·Poppler는 60초, Audiveris는 180초 제한이며 시간 초과 시 자식 프로세스 그룹까지 종료한다.
한글 글꼴을 검사하고 결과물도 눈으로 확인한다.

## 남은 한계

- 사진 한 장, JPG·PNG·WebP, 12MiB 이하만 지원. PDF·HEIC·다중 페이지 미지원.
- 인식 결과의 음표 직접 편집 기능은 없다. 장·단조와 제목·번호만 수정한다.
- OMR의 정확도는 보장할 수 없다. 67장 300DPI 렌더 이미지로 실제 연결을 시험했으며 한글 오인식이 있었다.
  실제 휴대폰 촬영본의 정확도 검수는 별도 작업이다.
- 변환된 기본 악보는 출판 악보와 전체 대조 전이다. 일부 표현은 경고하고 일부는 변환을 거절한다.
- 기본 자료는 전체 권리 확인이 완료된 공개 배포 데이터셋이 아니다. 이전 조사 맥락은 소스 조사 문서에 남아 있다.
- 단일 앱 + 단일 worker 구성. 여러 worker를 쓰기 전 작업 복구·렌더 잠금 설계를 확장해야 한다.

실행, 가져오기, 80곡 검사, 저장·이전 방법은 [README](../README.md)를 따른다.
세부 요구와 검증 기록은 [사진 분석과 개인 보관함](photo-library-spec.md)을 참고한다.
