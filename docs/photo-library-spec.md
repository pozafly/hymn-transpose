# 사진 분석과 개인 악보 보관함

2026-09-24 사용자 요구사항과 구현 기록. 아래 목표 설계에서 남은 제한은 문서 하단에 구분한다.

## 사용 목적

장모님 한 분이 URL로 접속해 개인적으로 사용하는 악보 도구다.
기존 찬송가의 검색·조 선택·PDF/PNG 다운로드를 유지하면서 사진 분석을 추가한다.

- 새찬송가 645곡을 기본 자료로 등록한다. 원본 확보와 변환·검수 완료 여부를 구분한다.
- 사용자가 악보 사진을 올리면 악보 데이터를 분석한다.
- 분석 결과로 여러 조의 악보를 생성하고 미리보기·다운로드를 제공한다.
- 올린 원본과 분석 결과, 생성한 조를 보관해 다음 접속에서도 검색한다.
- 같은 찬송가라도 기본 자료와 사용자 업로드는 서로 독립된 검색 결과다.

## 식별과 검색

찬송가 번호는 곡을 찾기 위한 메타데이터이지 악보의 고유 ID가 아니다.
각 기본 악보와 업로드마다 별도 scoreId를 부여한다. 제목이나 번호가 같아도
기존 항목을 덮어쓰거나 자동 병합하지 않는다.

예를 들어 67장 검색 결과는 다음 두 항목을 동시에 포함할 수 있다.

- 67장 · 영광의 왕께 다 경배하며 · 기본 찬송가
- 67장 · 영광의 왕께 다 경배하며 · 내 악보 · 등록 날짜

각 항목 안에 F, G 등 생성된 조를 표시한다. 조별 결과를 별도 곡으로 세지 않는다.
제목·찬송가 번호는 사용자가 수정할 수 있게 하고 번호 없는 일반 악보도 허용한다.

## 사용자 흐름

1. 로그인 후 기본 찬송가와 내 악보를 함께 검색한다.
2. 사진을 선택하고 제목, 선택적 찬송가 번호, 생성할 조들을 지정한다.
3. 업로드와 분석 진행 상태를 보여준다. 페이지를 나가도 작업과 원본은 보존한다.
4. 분석 결과를 원본과 비교한다. 인식 완료는 정확도 검증 완료를 의미하지 않는다.
5. 분석 결과를 확인한 뒤 선택한 조들을 생성한다.
6. 생성된 조를 전환하며 악보를 보고 PDF/PNG를 내려받는다.
7. 실패 시 원본을 유지하고 재시도할 수 있다. 일부 조만 실패하면 성공한 결과는 유지한다.

## 저장 구조와 작업

- Score: 고유 ID, 기본/개인 구분, 제목, 찬송가 번호(선택), 소유자, 등록 날짜.
- Source: 업로드 원본, 인식 엔진/버전, MusicXML 등 구조화된 분석 결과.
- Revision: 분석을 재실행하거나 내용을 수정할 때 새 버전. 기존 결과와 구분한다.
- Job: 대기/분석 중/확인 필요/생성 중/완료/실패, 오류, 재시도 횟수.
- Render: scoreId + revision + 목표조 + 렌더러 버전으로 캐싱한 PDF/PNG.

작업 상태는 메모리만이 아니라 영속 저장소에 기록하고 재시작 시 중단 작업을 복구한다.
사진 분석과 악보 조판은 웹 요청 수명과 분리해 제한된 동시성으로 처리한다.

## 기술 조건

Next.js + Node.js + pnpm을 유지한다. 음표의 조옮김은 LilyPond의 `\transpose`가 한다.
기존 67장 템플릿의 원조와 레이아웃은 그대로 보존한다.
새 악보는 인식된 원조·장단조·박자·성부를 갖는 별도 소스를 생성한다.

사진에서 악보를 읽는 엔진은 기존 omr/ 음표머리 검출기와 별개다.
Audiveris는 Python 없이 실행 가능한 후보이며, 사진 → MusicXML 결과를 검증해야 한다.
MusicXML → LilyPond 연결은 Python 기반 musicxml2ly에 의존하지 않는 경로가 필요하다.
외부 AI 분석 허용 여부는 사용자에게 질문했다. 아직 답변이 없어 자체 서버 분석 경로를 우선 시험했다.

업로드된 텍스트나 엔진 출력의 LilyPond 코드를 그대로 실행하지 않는다.
구조화된 데이터를 검증하고 허용된 문법으로만 소스를 생성한다.
분석/조판에는 타임아웃과 자원 제한을 적용한다.

## 비공개 접근

가족 전용 계정만 접근한다. 화면, 목록, 업로드, 작업 상태, 원본, 분석 결과,
PDF/PNG 모두 서버에서 인증한다. 파일 경로 자체를 공개 저장소로 노출하지 않는다.
공유 HTTP 캐시에 개인 악보를 저장하지 않고 내부 렌더 캐시는 유지한다.

## 검증 기준

- 같은 번호의 기본 악보와 업로드 두 건이 검색에 각각 나타난다.
- 업로드 재시도는 해당 작업을 재실행하고, 새 업로드는 별도 항목을 만든다.
- 재접속/서버 재시작 후에도 원본과 완료 결과를 조회할 수 있다.
- 선택한 여러 조의 결과가 보존되고 부분 실패를 개별 재시도할 수 있다.
- 로그아웃 상태에서 직접 파일 URL과 API를 호출해도 자료를 받을 수 없다.
- 실제 찬송가 사진으로 음표, 임시표, 박자, 성부, 코드, 한글 가사를 대조한다.
- 읽지 못한 요소를 조용히 생략하거나 추측으로 채워 성공으로 표시하지 않는다.

## 초기 엔진 시험 (2026-09-24)

[Audiveris 5.11.0](https://github.com/Audiveris/audiveris/releases/tag/5.11.0)의
공식 macOS arm64 배포본을 임시 디스크 이미지에서 실행했다. 이 초기 시험 당시에는 웹앱 연결 전이었다.
Tesseract의 한국어·영어 언어 데이터를 설치하고 `kor+eng`으로 시험했다.

입력은 카메라 사진이 아닌, 현재 앱의 67장 F장조 PDF를 PNG로 변환한 이미지다.
따라서 이번 결과를 실제 휴대폰 사진의 정확도나 처리 시간으로 일반화할 수 없다.

- 150 DPI (1241×1754): 오선 간격 10px가 너무 작다는 경고와 함께 분석 실패.
- 같은 PDF의 300 DPI 이미지: 약 10.4초 후 압축 MusicXML 파일 생성.
- 출력: 유음표 174개, 가사 요소 166개, 코드 요소 8개, 2개 파트의 마디 요소 총 44개.
- 두 파트의 조표는 F장조에 해당하는 fifths=-1, 박자의 beats는 3으로 출력됨.
- 한글 문자열이 포함되어 있지만 음표·가사·코드의 정확도는 대조하지 않음.
- 메트로놈 인식/내보내기 경고와 `chi_tra` 언어 데이터 로드 실패 메시지가 있었음.
- 종료 코드 0과 MusicXML 생성만으로 분석이 정확하다고 처리하면 안 됨.

초기 시험 입력과 결과/로그는 `/tmp/hymn-omr-*`에 있다.

## 이후 구현과 검증

- Linux Docker의 Audiveris → MusicXML → Node 변환 → LilyPond 경로를 웹앱에 연결했다.
- SQLite 작업 큐, 원본·결과 영속 저장, 서버 세션 인증, 중복 번호 검색을 구현했다.
- 데스크톱·모바일에서 실제 이미지 업로드, 분석 확인, F·G 생성, PDF 다운로드, 재접속과 중복 검색을 시험했다.
- 테스트 입력은 여전히 PDF를 래스터화한 67장 이미지다. 한글 가사의 오인식이 확인되었다.
- 원곡의 장·단조 선택으로 조표만 읽은 OMR 결과를 보정할 수 있다. 음표·가사 편집은 미구현이다.
- 기본 악보 645개 중 성공·기존 등록 641개, 실패 4개. 사용자 요청에 따라 생성 검사는 1~80장으로 한정한다.
- 실제 카메라 사진 대조, 전체 악보의 음악적 검수, 다중 페이지 지원, 음표 편집은 남아 있다.
- 데이터와 생성물은 Git에서 제외하며 실행·이전 절차는 루트 README에 정리했다.

### 업로드 전처리 회귀 수정

Linux에서도 같은 300DPI 원본은 가사 요소 166개를 읽었다. 하지만 업로드 전처리가
2481×3508 이미지를 2480×3507로 줄이면 가사 요소가 7개로 감소했다.
따라서 작은 이미지의 확대를 하지 않고, 2500×3508 안에 들어오는 원본의 픽셀 크기를 보존한다.
큰 사진만 이 범위로 축소한다. 표준 테스트 입력의 가사가 100개 이상 인식되는지도 E2E에서 확인한다.
이는 해당 입력의 회귀 검사이며 실제 카메라 사진 정확도 보장은 아니다.

최종 검증: 1~80장 각각 기본 조의 PDF·모든 PNG 검사 80/80 통과,
단위 테스트 11개와 데스크톱·모바일 E2E 12개 통과. 원본 이미지 크기 보존과
가사 100개 이상 인식, 장단조 변경, F/G 생성, `67장` 정확한 번호 검색을 포함한다.
